# M4: Zotero Reader Design

## Summary

This milestone implements read-only access to Zotero library data by building a `ZoteroReader` class that coordinates three data sources: a pre-exported CSL-JSON file for bibliographic metadata, Better BibTeX's SQLite database for citekey-to-itemID mapping, and Zotero's main SQLite database for attachment file paths. The reader serves as a data source for the existing `Library.add()` ingestion pipeline rather than implementing a new protocol, allowing future batch import and CLI commands to simply iterate over citekeys and invoke the standard add path.

The implementation prioritizes pragmatic reuse of existing infrastructure. By leveraging Better BibTeX's CSL-JSON export rather than parsing Zotero's complex EAV schema directly, the reader focuses on two narrow database queries: resolving citekeys to internal IDs and mapping those IDs to attachment paths. Database locking is handled with a copy-if-locked strategy that falls back to temporary copies when Zotero is running. The result is a standalone reader that provides structured access to Zotero items (metadata + attachments) without writing back or requiring Zotero to be closed.

## Definition of Done

**Primary Deliverable:** A `ZoteroReader` Python class that provides read-only access to Zotero library data by:
- Parsing `library.json` (CSL-JSON export) for bibliographic metadata
- Querying `better-bibtex.sqlite` to map citekeys → Zotero item IDs
- Querying `zotero.sqlite` to resolve attachment paths (returning all attachments per item)
- Handling database locking (copy-if-locked when Zotero is running)

**Success Criteria:**
- Can retrieve CSL-JSON metadata for any item by citekey
- Can retrieve all PDF attachment paths for any item by citekey
- Gracefully handles edge cases: items without attachments, orphaned attachments, non-PDF attachments
- Tests pass for citekey lookup, attachment resolution, and edge cases

**Out of Scope (deferred):**
- CLI commands for Zotero operations
- Batch import functionality
- Writing back to Zotero
- Direct CSL-JSON construction from Zotero's EAV tables (using export instead)

## Glossary

- **CSL-JSON**: Citation Style Language JSON format—a standardized bibliographic metadata schema used by Zotero, Pandoc, and citation processors. Contains fields like title, author, issued date, and publication information.
- **Better BibTeX**: A Zotero plugin that generates stable citation keys (citekeys) for each library item and can auto-export the library to CSL-JSON format.
- **Citekey**: A human-readable, stable identifier for a bibliographic item (e.g., `Smith2023`). Generated by Better BibTeX and used as the primary lookup key in this system.
- **EAV schema**: Entity-Attribute-Value schema—Zotero's internal database structure where item metadata is stored as key-value pairs in joined tables rather than fixed columns. Complex to query directly.
- **Attachment link mode**: Zotero's classification for how attachments are stored: `0` = imported into Zotero storage, `1` = linked to external file, `2` = linked URL. Affects path resolution.
- **SQLite URI mode**: SQLite connection parameter (`?mode=ro`) that opens a database in read-only mode, preventing accidental writes and allowing shared access.
- **`SQLITE_BUSY`**: SQLite error code indicating the database is locked by another process. Triggers the copy-if-locked fallback strategy.
- **XDG-compliant paths**: File system layout following the XDG Base Directory Specification—standardized locations for config, cache, and data files on Unix-like systems.
- **Context manager protocol**: Python pattern using `__enter__` and `__exit__` methods to enable `with` statement usage for automatic resource cleanup.
- **Frozen dataclass**: Python dataclass with `frozen=True` parameter, making instances immutable after creation. Requires tuples instead of lists for collections.

## Architecture

ZoteroReader is a standalone class that provides read-only access to Zotero library data. It serves as a data source for the standard `Library.add()` path rather than implementing the `ContentAcquirer` protocol.

**Data Flow:**
```
library.json (CSL-JSON export)
    │
    ▼
┌─────────────────┐      better-bibtex.sqlite
│  ZoteroReader   │◄─────(citekey → itemID)
└─────────────────┘
    │                    zotero.sqlite
    │◄───────────────────(itemID → attachments)
    ▼
ZoteroItem(csl_json, attachments)
    │
    ▼
Library.add(attachment.path, metadata=csl_json)
```

**File Location:** `src/local_library/ingestion/zotero.py`

The reader coordinates three data sources:
1. `library.json` — Pre-exported CSL-JSON from Better BibTeX
2. `better-bibtex.sqlite` — Maps citekeys to Zotero itemIDs (indexed on `citationKey`)
3. `zotero.sqlite` — Resolves itemIDs to attachment file paths

**Why this architecture:**
- Leverages existing CSL-JSON export (no complex EAV schema transformation)
- Single responsibility: reader only reads, `Library.add()` handles ingestion
- Future batch import iterates `list_citekeys()` and calls add for each
- Future CLI (`add --zotero citekey`) wraps the same path

### Data Model

```python
@dataclass(frozen=True)
class ZoteroAttachment:
    """A single attachment from a Zotero item."""
    path: Path                    # Resolved absolute path to file
    filename: str                 # Original filename
    content_type: str             # MIME type (e.g., "application/pdf")
    attachment_key: str           # Zotero's 8-char key for this attachment
    link_mode: int                # 0=imported, 1=linked, 2=linked_url, etc.

@dataclass(frozen=True)
class ZoteroItem:
    """Complete item data from Zotero, ready for Library.add()."""
    citekey: str                  # Better BibTeX citekey (lookup key)
    csl_json: dict[str, Any]      # Full CSL-JSON metadata
    attachments: tuple[ZoteroAttachment, ...]  # All attachments (immutable)
    zotero_key: str               # Zotero's 8-char item key
    item_id: int                  # Zotero's internal itemID
```

Design decisions:
- `attachments` is a tuple (not list) for true immutability with `frozen=True`
- Both `zotero_key` and `item_id` included—key is stable across syncs, ID is for joins
- `link_mode` preserved so callers can filter (e.g., skip linked URLs)

### Core Interface

```python
class ZoteroReader:
    """Read-only access to Zotero library data."""

    def __init__(
        self,
        zotero_dir: Path,
        library_json_path: Path | None = None,  # Defaults to zotero_dir/library.json
        temp_dir: Path | None = None,           # For database copies when locked
    ): ...

    # Primary API
    def get_item(self, citekey: str) -> ZoteroItem: ...
    def list_citekeys(self) -> Iterator[str]: ...
    def has_item(self, citekey: str) -> bool: ...

    # Resource management
    def close(self) -> None: ...
    def __enter__(self) -> "ZoteroReader": ...
    def __exit__(self, ...): ...

    # Cache management
    def refresh(self) -> None: ...
```

### Database Access Strategy

Zotero locks its SQLite databases while running. The reader handles this with copy-if-locked:

1. Try to open database directly (read-only mode via `?mode=ro` URI)
2. If locked (`SQLITE_BUSY`), copy to temp location and open copy
3. Cache connections for reuse within a session
4. Clean up temp copies on `close()` or context manager exit

## Existing Patterns

Investigation found these patterns to follow:

**Protocol-based architecture** (`src/local_library/ingestion/base.py`):
- `ContentAcquirer` and `ContentExtractor` protocols for duck typing
- ZoteroReader doesn't implement these (standalone reader, not an acquirer)
- But follows same structural pattern: `can_handle()`, `validate()`, then operation

**Error handling** (`src/local_library/core/errors.py`):
- `LocalLibraryError` base with `ErrorCode` enum and `details` dict
- Domain-specific subclasses: `AcquisitionError`, `LookupError`, `MetadataError`
- ZoteroReader will add Zotero-specific error codes

**Frozen dataclasses** (`src/local_library/core/models.py`):
- All result types are `@dataclass(frozen=True)`
- `ZoteroItem` and `ZoteroAttachment` follow this pattern

**Configuration** (`src/local_library/config.py`):
- XDG-compliant paths via `platformdirs`
- Pure functions for getters, separate mutation

**Testing** (`tests/integration/conftest.py`):
- Fixtures for external resources in integration tests
- Temporary directories for isolation

## Implementation Phases

### Phase 1: Data Model and Error Codes

**Goal:** Establish types and error infrastructure for Zotero integration.

**Components:**
- `ZoteroAttachment` and `ZoteroItem` dataclasses in `src/local_library/ingestion/zotero.py`
- New `ErrorCode` values in `src/local_library/core/errors.py`:
  - `ZOTERO_DIR_NOT_FOUND`
  - `ZOTERO_DATABASE_NOT_FOUND`
  - `ZOTERO_DATABASE_LOCKED`
  - `ZOTERO_DATABASE_ERROR`
  - `ZOTERO_LIBRARY_JSON_NOT_FOUND`
  - `ZOTERO_LIBRARY_JSON_PARSE_ERROR`
  - `ZOTERO_ITEM_NOT_FOUND`
  - `ZOTERO_CITEKEY_NOT_IN_BBT`
  - `ZOTERO_ATTACHMENT_MISSING`

**Dependencies:** None (first phase)

**Done when:** Types importable, error codes defined, unit tests pass for dataclass creation

### Phase 2: Library JSON Parsing

**Goal:** Load and query CSL-JSON metadata from Better BibTeX export.

**Components:**
- `_load_library_json()` method — parses JSON, builds citekey → metadata index
- `_get_metadata(citekey)` method — returns CSL-JSON dict or None
- Metadata caching for repeated lookups
- `refresh()` method to reload after export updates

**Dependencies:** Phase 1 (data model)

**Done when:** Can load `library.json`, lookup metadata by citekey, handle parse errors gracefully, tests pass

### Phase 3: Database Connection Handling

**Goal:** Safe read-only access to Zotero SQLite databases with copy-if-locked fallback.

**Components:**
- `_get_connection(db_name)` context manager — opens connection, handles locking
- `_copy_to_temp(db_path)` helper — copies locked database to temp dir
- Connection cleanup in `close()` and `__exit__`
- Read-only enforcement via SQLite URI mode

**Dependencies:** Phase 1 (error codes)

**Done when:** Can open both databases, handles locked state by copying, cleans up temp files, tests pass

### Phase 4: Citekey to ItemID Resolution

**Goal:** Map Better BibTeX citekeys to Zotero item identifiers.

**Components:**
- `_lookup_in_bbt(citekey)` method — queries `better-bibtex.sqlite` citationkey table
- Returns tuple of `(item_id, zotero_key)` or raises `LookupError`
- Uses indexed `citationKey` column for efficient lookup

**Dependencies:** Phase 3 (database connections)

**Done when:** Can resolve citekey to itemID, handles unknown citekeys, tests pass with mock BBT database

### Phase 5: Attachment Resolution

**Goal:** Resolve Zotero itemID to file system paths for all attachments.

**Components:**
- `_get_attachments(item_id)` method — queries `zotero.sqlite` for attachment records
- Path resolution: `storage:<filename>` → `<zotero_dir>/storage/<attachment_key>/<filename>`
- Handles multiple attachments per item
- Includes all attachment types (caller filters by `content_type` or `link_mode`)

**Dependencies:** Phase 3 (database connections)

**Done when:** Can resolve itemID to attachment paths, handles items without attachments, tests pass with mock Zotero database

### Phase 6: Public API Integration

**Goal:** Wire everything together into the public `ZoteroReader` interface.

**Components:**
- `__init__` with validation — checks Zotero directory exists
- `get_item(citekey)` — orchestrates metadata lookup, BBT resolution, attachment resolution
- `list_citekeys()` — iterates all keys from library.json
- `has_item(citekey)` — existence check without full load
- Context manager protocol (`__enter__`, `__exit__`)

**Dependencies:** Phases 2, 4, 5

**Done when:** Full `get_item()` flow works end-to-end, all public methods tested, integration tests pass with mock Zotero directory

## Additional Considerations

**Attachment selection (deferred):** Items with multiple PDFs will need selection logic for batch import. Current design returns all attachments; selection logic will be added when batch import is implemented. Possible strategies include: largest file, exclude "supplementary" in filename, user-designated primary.

**Staleness of library.json:** The CSL-JSON export must be kept up-to-date manually (Better BibTeX auto-export or manual refresh). The `refresh()` method reloads the cache but doesn't trigger Zotero export. Consider documenting recommended export settings for users.

**Database schema stability:** Zotero 7's core schema (items, itemAttachments) appears stable. Better BibTeX's citationkey table structure is straightforward. Both should be monitored after major version upgrades.
